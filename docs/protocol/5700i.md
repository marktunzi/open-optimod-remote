# 5700i interoperability notes

Reference: device firmware 3.0.1.20, document version 5700.51, matching Windows PC Remote SHA-256 `63def9bbe3ea4cc5714b958a330f511e9f8540b973f0cedaf596dd7956054b43`. Analysis uses a locally installed reference; no proprietary program is distributed or required at runtime.

## Session and framing

PC Remote uses TCP 6201. Login is `connect`, LF, the legacy-obfuscated uppercase access code, LF, NUL. The access-code transform starts with state 123456 and updates `(state * 419 + 6173) % 29282` per byte. XOR with the low byte, preserving a byte that would become zero. This is legacy obfuscation, not transport security. The current implementation intentionally supports only tested ASCII access codes.

A login can also be answered `busy` (the unit is still closing a previous session) or `in use`. The original client reports these as "… is busy." and "… is in use."; the app names them and tries a `busy` login once more after 1 s.

Successful login returns four LF-separated lines: success marker, access level, model/firmware and session seed. Failure responses can terminate with NUL. Access level zero was tested. Other write permission levels remain disabled.

Every subsequent frame has a five-byte header and a 1–65535 byte body. For body-length bytes `hi`, `lo`, header bytes are `hi ^ 0x1a`, `-hi ^ 0xc2`, `lo ^ 0x67`, `-lo ^ 0xa8`, and the negative sum of those four bytes, with byte wrapping. Validate both complement pairs and the checksum. Do not attempt recovery from corrupt framing on a live control connection. The one exception is a frame the unit ends early (see [Frames the unit cuts or drops](#frames-the-unit-cuts-or-drops)): it is recognised only where a valid header and `%8d%8d` protocol-6 prefix start inside it.

The body starts with two eight-character decimal fields: opcode minus 204 and protocol type 6. Known operations:

| Request | Meaning | Response |
|---|---|---|
| 218 | Disconnect | Connection closes |
| 219 | Poll / heartbeat | 220, or subscribed meter frames |
| 222 / 223 | Enable / disable session meters | Subscription state |
| 227 | Typed parameter change | Ordered 250/251 boundary; exact readback when required |
| 239 | Fetch on-air archive (the saved file; whole only with meters off) | 229 named `OnAir.orb57onair` |
| 240 | Fetch setup archive | 233 |
| 250 | Ordered response boundary | 251 |

Do not infer that other opcodes are read-only. In particular, 226 and bulk preset operations have save/flush side effects and are not used by this development UI.

## Changes and confirmation

A parameter change is `NAME;INDEX;TYPE:VALUE;SCOPE;`. Scope 1 is processing; 2 is system. Examples use synthetic values or a non-audio control. `CONTRAST;2;Int:2;2;` changes display contrast to index 2. Its allowed indices are 0–3, not 0–4. String types use angle delimiters, such as `String:<Independent>;`.

A response boundary confirms that the PC Remote stream has processed everything before it; it is not a field-by-field terminal document. Interactive single-field writes first compare host, session, preset and prior field against the app's last confirmed document, send opcode 227 once, then require the 250/251 boundary and update that guarded cache. If the boundary fails, the independent terminal status interface reads actual processing (`AP [code]??`) or system state (`AS [code]??`) to resolve the outcome. Fields outside the hardware-verified profile (the statically derived supplement in `profiles/5700i/3.0.1.20/static-parameters.json`, such as the two-band structure and the MX structure of the paid MX upgrade) always take that exact readback, even after a successful boundary. Manual refresh, preset export/application and explicit hardware verification also use exact documents. A timeout has an unknown outcome and must not trigger an automatic retry.

Do not take AP/AS snapshots before and after every successful interactive write. On the reference firmware each full terminal document suspended live meter responses for roughly 570 ms. Removing those routine snapshots reduced the measured write-related meter gaps from two pauses of about 568–600 ms to 103–189 ms, the remaining interval being the processor's own opcode-227 work. The canvas keeps interpolating the last real packets during that short interval; it never invents signal values.

On the reference Mac and device, the standalone native check changed contrast 3 → 2 → 3 and verified that all 222 processing and 178 system fields matched the baseline afterwards. The same check passed through browser keyboard input. A later reversible processing check changed `B2 OUTPUT MIX` by 0.1 dB and restored it with exact readback while the session and meters remained live. Recall was verified on the reference unit on 20 October 2026 ([Recall keeps the session](../verification/2026-10-20-recall-session.md)). Routing, coupling, text and firmware writes have not been hardware-verified.

## Session lifetime

Connecting is the PC Remote login. The AS and LP/AP terminal reads that follow are a separate step: when the status port is closed or silent, the session stays connected with live meters but without documents, so writes and Recall are refused until a Refresh succeeds.

End a session with `218`, a half-close, and reading until the unit closes (at most 1 s). Closing with replies still unread resets the connection while the unit is still sending, and after a few of those the unit refuses every TCP connection on 6201 and 23 for about a minute. After a connection reset, the unit can stay unavailable for minutes while new logins keep arriving; leave it alone for about two minutes before reconnecting. The app therefore reconnects automatically only after an unexpected loss, first after 120 s and then with doubling waits, and closes an unfinished login with a reset so it cannot remain half-open on the unit. See [Phase 1 session](../verification/2026-10-20-phase1-session.md).

## Frames the unit cuts or drops

Observed on the reference unit and on the virtual 5700i running the same original firmware (20 October 2026):

- **While session meters are on (222), the unit sends at most what fits its send buffer.** A longer frame announces its full length but stops early, and the next frame starts right after the last byte sent. The pushed document after a terminal `RP` stopped at 4096 wire bytes on the reference unit; on the virtual unit it stopped at 4075, with a 21-byte `251` before the next frame at 4096. While switching presets the virtual unit also cut meter records at arbitrary points (17, 22, 76, 92, 97, 111, 116 and 117 of 138 bytes in two captures).
- **With session meters off (223), a requested archive arrives whole** (5 of 5 on the virtual unit, 7632 bytes). With meters on, the same request was cut at 4096 bytes every time after a recall.
- **The unit can drop a whole frame**, a `251` among them, when its buffer is full. A boundary that the unit will never answer must not keep the session waiting.
- **The cut is not limited to one opcode.** The decoder of the 5700i adapter therefore ends any frame where a real frame starts inside it, and never interprets the cut body except to decrypt its complete blocks (below). A frame that is followed by bytes that are not a frame is still corrupt.

A raw capture of the virtual unit during a terminal recall is a test fixture (`crates/orban-protocol/tests/fixtures/5700i-virtual-recall-capture.bin`).

## Changes made elsewhere

A terminal `RP`, a front-panel recall or automation makes the unit push the new on-air document as opcode 229 with an empty file name. With meters on, it arrives cut, but its complete AES-CBC blocks decrypt: the start of the virtual unit's push read `Preset Name=<GREGG>` followed by the first fields. Pushed files end lines with LF; terminal documents with CR LF.

Opcode 239 returns the saved file `OnAir.orb57onair`, whose fields equal the terminal AP document field for field (222 fields, virtual unit). The unit writes that file a moment after a change: right after a recall a 239 read returned the previous preset. The app therefore:

1. ignores a push whose decrypted start agrees with the shown document (its own Recall);
2. otherwise withdraws the shown document, which refuses processing writes, Recall and preset management;
3. reads the archive with meters off (223, 239, then 222) 2 s later, up to five times, and accepts it only when its name and the fields of the push agree;
4. never opens a terminal session for this. On the virtual unit, a second terminal session opened right after another client's `RP`, while that client was still connected, left the terminal server without any answer (TCP 23 accepted, no banner) until the unit was restarted. This was seen twice; the first time another test also used the unit, the second time it did not.

## Meter messages

Response 228 contains a raw bank byte, decimal count followed by LF, and that many binary bytes. The observed profile has 112 channels per bank. Banks 1 and 2 must **not** be interpreted as FM and HD: both contain channels from both processing paths. The UI converts bank 1 with channel-specific reference curves; see [meter conversions](../meter-curves.md). Current/peak bank semantics, some absolute HD/loudness axes and every indicator still require reference comparison.

Verified reference channel identifiers include input L/R 1/2, AGC bass/master L 3/4, FM bands 1–5 L 5–9, FM output L/R 27/28, HD bands 1–5 L 39–43, and HD limiting L/R 19/20. Other channels, right-channel gain reduction, gate flags, output scales and peak behavior remain part of the parity work.

A native 30-second test received 286 frames from each bank, with 256 changing frames in each bank; the slowest observed poll cycle was 219 ms. A later UI-path measurement averaged 55.3 ms between distinct frames and showed that requesting every 25 ms did not increase the processor's output rate. The runtime therefore polls every 50 ms and interpolates display motion between real packets. These are smoke tests, not the required eight-hour soak or a Windows latency comparison.

## Archives

File bodies contain two decimal timestamp words, filename/path metadata and byte count, each LF-delimited, followed by exactly the specified binary data. Firmware 3.0.1.20 can return Windows-style absolute paths and can emit an empty filename for a preset-change event. These are accepted as bounded metadata but are never resolved or used as local paths or filenames.

Observed archives use AES-256 CBC with ciphertext stealing for a partial last block, prefixed by a 16-byte IV. The access code is repeated to form the 32-byte key. This scheme does not authenticate content. Decrypted documents must pass structural checks; successful decryption alone does not establish integrity.

Documents contain typed fields with device indices. Keep Cent values as integer hundredths, preserve enum indices and retain original metadata. The embedded 366-field profile was derived from static pure conversion routines and cross-checked against current device values. It is not a complete specification of visibility, coupling, defaults for all algorithms, or optional hardware.

## Equalizer value conversions and units

Reference conversion routines establish these index-to-wire mappings. Values below are wire values; `Cent` is divided by 100 for display. No Windows executable is needed at runtime.

- Low bass frequency: 35 integer values, 80–145 in steps of 5, 150–240 in steps of 10, 250–330 in steps of 20, 350–500 in steps of 30.
- PEQ low frequency: 47 values, `Cent(10 * trunc(200 * 25^(index/46)))`, displayed in Hz.
- PEQ mid frequency: 46 values, `Int(trunc(250 * 24^(index/45)))`, displayed in Hz.
- PEQ high frequency: 39 values, `Cent(10 * trunc(10 * 15^(index/38)))`, displayed in kHz.

FM and HD use the same frequency conversions. Reference identities: low bass 0x48d850, PEQ low 0x48c880, mid 0x48c8f0, high 0x48c950. The numeric conversion truncates toward zero. Static ranges are embedded so runtime math-library differences cannot alter a transmitted value. The current device values were cross-checked; exhaustive hardware sweeps and an interactive Windows comparison remain outstanding. Numeric units are retained separately from wire values and never appended to choice labels such as Off.

## Preset catalog and recall

The catalog exchange sends authenticated LP followed by AP on one connection. The complete AP document marks the response boundary, avoiding idle-time heuristics on a fragmented preset list. Recall validates the requested name and expected on-air identity against that session-owned catalog/document; it does not repeat LP/AP immediately before the write. It sends documented `RP NAME[CODE]` followed by AP in one terminal transaction, requires an `ON AIR: NAME` acknowledgment and a matching AP document, and publishes that returned document directly as the new processing state and comparison baseline.

A terminal `RP` (like a Recall from the front panel) makes the unit push the new on-air document on every open PC Remote session as an unsolicited opcode 229 file with an empty name, cut while meters are on (see [Frames the unit cuts or drops](#frames-the-unit-cuts-or-drops)). Trusting the announced length swallowed the following replies and lost the session about 14 seconds after a Recall. The push that follows the app's own Recall agrees with the AP document the Recall read and changes nothing. See [Recall keeps the session](../verification/2026-10-20-recall-session.md). Polls are still paused during the RP/AP transaction, but the unit answers them again as soon as they resume. After the complete AP document arrives, send opcode 222 once to re-enable session meters and reset the normal polling interval so its first tick occurs 50 ms later. Selection alone sends no write. Errors never trigger retries. If the combined response is unusual, one direct AP read while polling remains paused determines whether the selected preset is on air.

## Local preset export and application

The app exports a fresh validated AP document as a locally named file with the model's extension (`.orb57user` for the 5700i). It does not use an undocumented named-save opcode. Applying a local file parses the complete document, validates every imported field against the active firmware profile, checks host/session/current-preset guards, orders `HD COUPLING` ahead of dependent HD fields and writes each field once with opcode 227. It then reads the full AP document up to four times without replaying a write and requires every imported field to match exactly. Only a fully confirmed document becomes the new modified-state comparison baseline.

FM→HD coupling is not a blanket lock on every HD-named field. Per the official 5700i 3.0 Operating Manual, coupled presets make the HD equalizer and multiband compressor/limiter controls follow their FM counterparts, while the five controls in PC Remote's **HD Limiting** page remain independent: `IBOC EQ GAIN`, `IBOC EQ FREQ`, `IBOC LIM DR`, `HD DE ESS`, and `HD COUPLING`. The UI keeps that page available in coupled mode and preset import continues to write and verify those five fields.

This does not establish the named on-device Save, Save As, rename, delete, previous-preset or bulk backup commands. Opcode 226 remains unused.

## On-device preset management and backup

The 5700i firmware has no terminal save or delete command. Its PC Remote keeps presets in a local folder and syncs it with file messages. Static analysis of `5700iPC.exe` shows the file upload sending opcode 229, 230, 231, 233 or 234 depending on the file type, and preset deletion sending opcode 237 with newline-terminated names. The expected name form and any side effects are unknown, so the app sends none of these messages to a 5700i or 8700HD and does not offer on-device save, rename or delete for them. The OPTIMOD 5500 documents `SP NAME` and `DP NAME` in its terminal help; see the [static analysis](../research/2026-09-29-5500-8700hd-static-analysis.md#presets-op-het-apparaat-opslaan-en-verwijderen).

The app's backup is built from verified reads only: the AP and AS documents from the terminal plus the LP preset names. A restore writes system fields with the ordinary opcode-227 change, one write per differing field, never network settings, the running clock or `ACTUAL` status values, and then reads AS back up to four times without replaying a write. The encrypted archives from opcodes 239 and 240 are not needed for this.

## Additional parameter conversions

- AGC BASS COUPLE: index 0 is Choice Off; indices 1–13 are Int(13-index), unit dB (reference 0x490650).
- Both BS1770 LDNES CTRL THR fields: indices 0–200 become Cent((index-310)*10), unit dB (0x498070).
- DIVERSITY DELAY ADJ for the supported 5700i: indices 0–0xf833d become a Choice string formatted to nine decimals: (index+23361)/64000 seconds (0x4986d0, model branch 2; count initialized at 0x4ab0ff). UI entry snaps to one supported sample.
- Identity integer port ranges and RDS UECP site numbers are represented compactly rather than by enormous enumeration arrays.

Text changes retain their existing index and use UserString, reject delimiter/control/non-ASCII characters and validate fresh readback. Domain-specific validation beyond wire encoding is not yet exhaustive for all RDS and remote-contact text workflows.
