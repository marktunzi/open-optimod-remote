# 8400 interoperability notes

Reference: the original OPTIMOD-FM 8400 firmware 3.0.5 (software version 3.0.5.7) running in the Optimod emulator, and the original 8400 PC Remote 3.0. Two captures of the original client (9 and 21 October 2026: login, file sync, parameter edits, Save As, Recall, logout), static analysis of both programs (the PC Remote is the unit's own PEG GUI built for Windows; the protocol code is the same in both), and live probes of the unit on 21 October 2026. Addresses are firmware VAs (flat image, base 0x100000) unless marked PC (8400_pc.exe, base 0x400000).

The 8400 is an older generation than the rest of the PC Remote family. It shares the frame header and the `%8d%8d` body prefix (type, protocol 6), but nothing else: no text login, no terminal, no opcode files. The client works on copies of the unit's own files, read and written through a remote file API, and forwards GUI events.

## Session

PC Remote listens on **TCP 51200** (bytes `C8 00`, 0x136720), backlog 5. Meters and the clock go to the PC over **UDP, port 16540** (see Meters).

| type (kind) | direction | payload |
|---|---|---|
| 0 (204) | PC → unit | the passcode, plain text |
| 1 (205) | unit → PC | login answer |
| 14 (218) | PC → unit | logout |
| 15 (219) | PC → unit | keepalive |
| 17 (221) | unit → PC | keepalive answer |
| 24 (228) | PC → unit | file call |
| 25 (229) | unit → PC | file call answer |
| 47 (251) | PC → unit | GUI event `wType;iData;text;` |
| 48 (252) | PC → unit | parameter change `NAME;index;Type:value;` |

Keep every frame to the unit within 4096 bytes; the unit's answers are capped at 4096 bytes.

### Login

The passcode is looked up as a control name in the unit's `password.pas` (`C:<ADMIN>UserString:<All screens>;D:0;`; ADMIN is the factory All Screens passcode). Found: `\n\n8400 Station Name: <name>\n8400 Software Version: 3.0.5.7\nAccess Level: <n>` and, with HD hardware, `\nHD Digital Radio Hardware Installed\n`. Not found: exactly `Invalid Passcode`, and the session stays open (another type 0 is evaluated again). An empty passcode gets no answer. The access level is the position of the passcode's level text in the `PASSCODE ACCESS LEVEL` list; 0 = All screens (observed). **The unit enforces nothing**: file calls, events and changes are served with or without a login; levels are enforced by the client. The app writes only at level 0. The original client requires software 3.0.0.0 or later.

### One session at a time, and how it ends

One thread serves one connection (0x136b10). New connections complete the TCP handshake in the listen backlog but are not read until the current session ends. A session ends only on **type 14** or **30 s without any received byte** (watchdog 0x1370b0). The unit ignores the peer closing or resetting the connection. The original client sends a keepalive every 2 s.

After type 14 the GUI thread closes the socket 200 ms later (0x1364f0) while the receive thread is already back in a blocking `recv()` on it. If the client's FIN has not arrived by then, the receive thread can stay blocked and the unit stops serving new sessions:

| End of a session (live, 21 October 2026) | Next login |
|---|---|
| type 14 and `shutdown` back to back | answered at once (6 of 6) |
| type 14, 1 s pause, `shutdown` | not answered; the unit's server was still stuck after 17 min (restart) |
| `Invalid Passcode`, then 14 after 10 s | not answered for ~5–6 min |

Each client that gives up during such a phase leaves a queued connection that the unit reads later and holds for ~31 s, so short retries keep it silent. The app therefore:

- sends a keepalive first and waits up to 5 s for its answer (the unit is serving this connection), then the passcode, and waits up to 35 s for the answer;
- never closes a connection before the unit has answered what it was sent: a connection it gives up on is kept, read until the answer arrives (up to 400 s), and then ended properly;
- ends every session with type 14 and `shutdown` back to back, then reads to EOF;
- ends a refused login the same way.

## File calls (24/25)

Request: `u16 function`, then each argument as `u16 length` + bytes, then `u16 0`. The answer echoes the function with its values in the same encoding; the first value is a 32-bit result. Strings carry their NUL. One call at a time; the original client waits forever, the app 10 s. Handles are unit heap addresses, passed back unchanged.

| fn | call | used for |
|---|---|---|
| 1 / 3 / 2 | `_findfirst` / `_findnext` / `_findclose` (280-byte `_finddata_t`, name at offset 20) | listing presets |
| 4 | `_chdir` | `c:\8400\user\`, `c:\8400\presets\50us presets\` or `75us presets\` |
| 5 | `_open(name, 0)` | read, and existence test |
| 8 | `_chmod(name, 0x180)` | before a write |
| 9 | `remove` | delete a preset |
| 12 / 14 / 19 / 18 / 13 | new stream, attach the descriptor, read the rest of the file, close, delete | reading a file |
| 24 / 28 / 30 / 27 / 29 / 26 | new output stream, buffer 0x1000, open, write, close, delete | writing a file |

Function 19 returns the file from the current position in text mode: one 0xFF per line pads the shortfall; the app reads up to `End Preset\n`. Function 27 takes `len = 0xFFFF` and the rest of the message as data (the unit also stores the closing `00 00`). There is no rename. All 31 functions are mapped in the research notes; the app uses only those above.

### Files

`c:\8400\user\`: `onair.orb` (on-air processing), `system.orb` (system settings), `next.orb`, `test.orb`, `time.orb`, `password.pas`, and one `<NAME>.orb` per user preset (its name is the `Preset Name` inside; file names are listed in upper case). Factory presets are `c:\8400\presets\{50us|75us} presets\<NAME>.ORB`; the original client chooses the folder from the system control `PRE-E`.

```
OptimodVersion=<00.08>
Preset Name=<TEST 02> size=126
Factory Preset Name=<ROCK-DENSE>
Preset Type= <ON AIR PRESET>
C:<SE AMOUNT>Cent:250;D:10;
...
End Preset
```

A modified on-air preset is named `M <name>`; the firmware drops the mark when the values match the preset again.

## Parameter changes (48)

`NAME;index;Type:value;` with the value as in the files (`Int:`, `Cent:` ×100, `String:<…>`, `UserString:<…>`), e.g. `SE AMOUNT;11;Cent:275;`, `PHASE ROTATOR;1;String:<Out>;`, `DI REF PPM LEVEL;37;Cent:-450;` (captured from the original client). The unit looks the name up in the on-air, system, test and time controls in that order, sets value and index, and runs the same handler as a front-panel edit. **It answers nothing.** It saves the change to `onair.orb` or `system.orb` 8–10 s later, which the app reads back to confirm (live: 10.5–11.7 s). `30 HZ HPF` exists as a processing and as a system control; a change always reaches the processing one, so the app does not change the system one.

The parameter tables come from the firmware's own conversion routines (`profiles/8400/3.0.5.7`, `scripts/extract_8400.py`).

## GUI events (47)

`wType;iData;text;`, one item, text up to 39 characters, no `;`. The unit posts it into its own GUI as if a front-panel action had raised it; iData is ignored.

| wType | meaning | text |
|---|---|---|
| 16395 (0x400B) | Recall | preset name |
| 16388 (0x4004) | Save: re-read `onair.orb`, `next.orb`, `<name>.orb` the client wrote | — |
| 16391 (0x4007) | preset added (after writing `<name>.orb`) | name |
| 16392 (0x4008) | preset deleted (after removing it) | name |
| 16390 (0x4006) | passcodes changed (after writing `password.pas`) | — |
| 16604 (0x40DC) | meters on | — |
| 16606 (0x40DE) | clock on | — |

Recall puts the named preset from the unit's own list on air (factory or user); the unit reports nothing, and the app confirms it from `onair.orb` (live: 10.8 s). The unit never reports front-panel edits or a restart either.

## Meters

After `16604;0;;` the unit sends a 34-byte UDP packet every 60 ms from an ephemeral port to the TCP peer's address, port 16540, until the session ends. Byte 0 = 1, then 29 values in a fixed order whatever the structure, then 4 status bytes. Values are the bar heights 0–100 of the unit's own meter screen.

| bytes | meters | scale |
|---|---|---|
| 1, 2 | input L, R | 0 / −3 / −7 / −10 / −15 / −20 / −40 dBFS at 100 / 83 / 67 / 50 / 33 / 17 / 0 |
| 3, 4 | output L, R | +3 / 0 / −3 / −7 / −10 dB at 100 / 75 / 50 / 25 / 0 |
| 5–8 | AGC bass L, master L, bass R, master R | gain reduction, 4 per dB |
| 9–18 | multiband bands 1–5, L and R | gain reduction, 4 per dB |
| 19–22 | two-band bass, master, limiter L, R | gain reduction |
| 23 | BS.412 MPX power | gain reduction |
| 24 | composite | 1.25 % per step |
| 25, 26 | AGC and multiband gate | non-zero = gated |
| 27 | Music/Speech | 0 speech, 255 music |
| 28, 29 | HD output L, R | inferred 0 to −12 dB |
| 30–33 | input source (1 analog, 2 digital, 3 digital + J17, 4 digital not locked), Music/Speech copy, sync 1, sync 2 | |

Type 2 packets (17 bytes, the unit's clock) follow `16606;0;;`; the app does not request them. Only one program on a Mac can receive port 16540; a second app instance connects without meters and says so.

## Save, Save As, Rename and Delete

From the original client's Save As (capture, 21 October 2026): it writes the on-air document three times through the write calls above (24, 28, 4, 8, 30, 27, 29, 26): `next.orb` with `Preset Type= <NEXT PRESET>` and the name `next.orb` already had, `onair.orb` with the new name and `<ON AIR PRESET>`, and `<NAME>.orb` with the new name and `<USER PRESET>`. Each ends `End Preset\n` and the closing `00 00`. Then it sends `16388;18;;` (Save). The app does the same, from `onair.orb` once the unit has saved what is shown. Delete removes the preset's own file (as the unit lists it: `EURO AC .ORB` holds `EURO AC`) and sends `16392;0;NAME;`. Rename is Save As followed by Delete. Checked on 29 October 2026 on the virtual 8400 3.0.5.7: Save As 5.2 s (listed, on air), Recall back 11.2 s, Delete 3.8 s; the unit's file set afterwards equals the one before.
