# 2300 interoperability notes

Reference: original OPTIMOD 2300 firmware 2.0.3.85 (document version 2300.20) running in the Optimod emulator, probed on 21 October 2026. A session of the original PC Remote 2.0.3.85 recorded by the emulator project (M17, connect and two Recalls) was decoded for comparison.

The 2300 is an older generation of the PC Remote protocol:

| | 2300 | 8700HD / 6300 |
|---|---|---|
| Login answer | `connect ok`, access level, `2300 V 2.0.3.85` — **no session number line** | four lines |
| Response boundary | 247 (F7h) / 248 (F8h) | 249 / 250 |
| On-air file | 237 (EDh) → 229 | 238 → 229 |
| Setup file | 238 (EEh) → 232 (E8h) | 239 → 232 |
| User preset files | 240 (F0h) → 231 (E7h) each | 242 → 231 |
| Password file | 241 (F1h) → 230 (E6h) | 243 → 230 |
| File message | `0\n0\n<size>\n` + file — **no name line** | `0\n0\n<name>\n<size>\n` |
| Meter record | bank byte, **count as one byte** (59), values | bank byte, decimal count line, values |
| Clock | 244 (F4h) every second | 246 |
| Terminal | **none**: TCP 23 refuses the connection | TCP 23 |

A poll (219) is answered by the meter record directly. Because files carry no names, the answer to a file request in flight is the requested file; a user preset's file name comes from the `Preset File Name` line inside its document.

## Recall

The original client recalls by uploading the preset as an unnamed on-air file (`0\n0\n<size>\n`, no end marker). For a factory preset it converts the installer's 2300.10 factory file (58 fields) into a 2300.20 document (56 fields, with other PEQ width indexes, `SE RATIO WIDTH` as Int, and so on) with its own tables. The unit has no terminal for `RP`. The app uploads the installer's factory file unconverted (`profiles/2300/2.0.3.85/factory-presets.json`, `.orb23f50` or `.orb23f75` by the system setting `PRE-E`, from `scripts/extract_factory_presets.py`): the firmware converts it itself, as it does for user presets saved as 2300.10. Checked on 29 October 2026 on the virtual 2300: after the original client's Recall of MUSIC HEAVY and after the app's, the unit's on-air file is byte-identical (the client's own upload equals that on-air file too).

User presets stored on the unit can be 2300.10 documents. The firmware converts them when it loads them, so after a Recall the on-air 2300.20 document differs from the uploaded one in the converted fields. A Recall is then confirmed by the preset name. With equal document versions the fields must still match exactly.

## Presets, Automation and Security (captures, 29 October 2026)

From `2300PC.exe` 2.0.3.85 on the virtual 2300 (original firmware), checked again with the app:

- **Save / Save As:** the on-air file with `Preset Name` and `Preset File Name` replaced, LF line ends, as an unnamed upload (229, `0\n0\n<size>\n`). The unit sends no boundary answer for it. The client then deletes the firmware's `modif …` working copies among the user files with one EBh (235) message, one `NAME.orb23user` line each.
- **Delete:** EBh with `NAME.orb23user\n`. The client does not offer to delete the preset on air.
- **Automation:** EFh (239) reads it; the client saves it as E9h (233) with `FILETIME low\nhigh\nsize\n` and no name line; `OptimodVersion=<2300.20>`, `auto_event_NN.orb23autom`. Actions after the presets: `Bypass`, `Exit Test`, `Stereo`, `Mono-R`, `Mono-L`, `Mono-Sum`, `Mod. Reduction 1`, `Mod. Reduction 2`, `Exit Mod. Reduction`. With no events left, the app deletes `Automation.orb23autom` with EBh; the firmware then sends no automation file (checked; the client's own removal was not captured).
- **Security:** F1h (241) is answered by E6h (230) `Password.orb23pas` (2300.20, the 5500i's level names); the client uploads E6h as `0\n0\n<size>\n`. Its *Automatic Lock* is the system setting `SECURITY TIMEOUT`, written as a parameter (227).
- **Diagnostics:** 204 with the access code, answered by 205; the client sends it right after the login, the app during its sync. The `Access Level` line is the unit's own state, not the session's: on the freshly started virtual 2300 (29 October 2026) every 204 got `0: all access`, from the app's sync and from a bare session, at once and 25 s after the login, and also in a session logged in with a level-5 passcode. In the long test session earlier that day the unit answered `7: undefined` to the original client's own 204 right after its login as well as to the app's. Client and app show the same text; the app's access level comes from the login answer, never from 205.
- **Backup:** EEh (setup, E8h), EFh (automation, E9h) and F0h (user files, E7h); the client writes each in plain text under the name the document gives itself (`Preset File Name`), the automation file as `Automation.orb23autom`, and keeps only `.orb23user` from the user file list (a `modif … .orb23f75` working copy is left out). The app's Backup gives the same files, byte for byte (checked against the client's backup folder).
- **Restore:** one E7h (231) per file with `FILETIME low\nhigh\nsize\n`, no name line and no boundary answer (meters off with DFh first). Checked with the app: a restored preset is listed and can be deleted again.
