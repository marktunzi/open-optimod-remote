# Open Optimod Remote 0.3.0 (limited scope, before full PC Remote parity)

0.3.0 is the first release with **signed automatic updates** and the native macOS app for **several processors at once** (one tab and session per processor). It is **not** a complete replacement for Orban's Windows PC Remote. The table below lists, per exact model and firmware, what was verified end to end and what is not offered in this version. Full per-model parity is the next stage of work ([#17](https://github.com/marktunzi/open-optimod-remote/issues/17)) and will reach installed copies through the update channel.

macOS 13 or later, Apple Silicon. Developer ID signed, notarized, hardened runtime.

## What is new since 0.1.0

- **Automatic updates (Sparkle 2):** a daily check and *Check for Updates…*. Every update and the update feed itself are signed. An update never ends a processor session by itself: with a processor connected you choose **Disconnect and Install** or **Later**. A postponed update installs when you quit, or from *Install Update…*. Connections, access codes and window positions stay.
- **Several processors at once:** a tab per processor in Meters and Processing Settings; System Settings, Presets and the Tools windows are one per processor; each session is separate.
- **Native macOS windows** for Connections (with groups), Presets, System Settings (the original client's Setup tabs per model), Automation, Security and Diagnostics.
- **Meters** follow the original clients: per-model layout, 2-band or 5-band groups by the on-air structure, gate lamps from each client.
- **Protocol coverage:** settings are synchronized from the processor's own files (no terminal session), preset recall works as the original client does it, and lost connections reconnect automatically.

## First launch

macOS asks once whether Open Optimod Remote may find devices on your local network. Choose **Allow**; without it every connection fails with *No route to host*.

Other models and firmware (5700 FM/HD, 8500, 8600, 9300, 9400, other versions of the models above) can be saved and identified, but are not supported. Changes are only offered where the table shows ✓.

Concurrent use was tested with up to three processors at once (two 6300s and an 8400; 5700i with 8700HD). No 8-hour soak was run for this release: a 77-minute three-session run found 8400 session drops, which are fixed in this release (see the [Phase 9 verification](../verification/2026-10-29-phase9-release-qa.md) and [8400 session stability](../verification/2026-10-29-8400-session-stability.md)).

No physical processor other than a 5700i (read-only) was available. Hardware acceptance and the remaining per-model checks are tracked in [#20](https://github.com/marktunzi/open-optimod-remote/issues/20); every row is in the [Phase 10 matrix](../verification/2026-10-29-phase10-matrix.md).

## Safety rules that still apply

- A setting is written only when the processor's current value matches what the app expects. Every change is read back, and a mismatch shows the processor's real value.
- Writes and recalls are never retried automatically.
- Access levels follow the original client of each model; a lower access level hides what it does not allow.
- Network settings stay read-only where the processor keeps them in its network file.
