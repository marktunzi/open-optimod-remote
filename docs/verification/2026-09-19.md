# Development verification, 19 September 2026

> **Evidence status:** Point-in-time protocol and implementation record. Use [HANDOFF](../HANDOFF.md), [5700i protocol](../protocol/5700i.md) and the 22 September reports for current behavior.

Target: Apple Silicon macOS and an OPTIMOD 5700i running firmware 3.0.1.20. Device credentials, network address and station/preset names are deliberately excluded.

## Verified in this milestone

- The reference processor returned 222 processing and 178 system fields. All 400 current values matched the embedded profile in a read-only comparison: 366 static mappings plus 34 typed text fields.
- The terminal preset catalog returned 76 entries. Catalog reading did not recall or alter a preset. Recall has explicit UI confirmation, on-air acknowledgment and AP readback, but was not executed on the running processor.
- Four physical output-source values were read. Routing editors are separated from local FM/HD/Both view tabs. No output route was changed.
- Named connection storage is implemented. Access codes are stored in a separate owner-only app-local credential file and never use Keychain. A successful connection receives a new random session token. Change and Recall requests must present that token, preventing a stale tab from writing to a newer connection on the same host.
- Setup fields are assigned exactly once to ten task-oriented groups and named subsections. Friendly labels, current values and field roles distinguish editable settings, device status and physical routing. Search spans every group.
- FM → HD processing coupling has an always-visible status and a two-step action. The mocked browser regression proved that opening the confirmation sends no write and that confirmation sends the captured field and session preconditions. The live processor's coupling state was read only.
- Channel-specific meter curves cover input, FM/HD output, limiting and FM/HD loudness paths. A critically damped display model bridges real packets across browser animation frames and clears malformed or data older than 1.2 seconds.
- In a short live measurement, distinct incoming meter frames averaged 55.31 ms apart, with a 51.24 ms median, 136.29 ms p95 and 245.64 ms maximum. Changing the request interval from 50 ms to 25 ms did not increase the processor's delivered rate, so the production target remains 50 ms.
- Allowing meter polling while terminal state refreshes reduced the longest observed refresh-related meter gap from approximately 2.85 seconds to 777 ms in the short comparison run. This is not a long-duration guarantee.
- A live read-only browser run exercised Processing, Presets, Outputs, every Setup category and every FM/HD processing page without browser exceptions or mutation requests. Automated geometry checks at 1440×900 and 1180×760 found no text overlap or horizontal content overflow. FM/HD/Both meter tabs did not change device routing.

- the production Vite build;

## Safety boundary

No audio processing, FM → HD coupling, physical routing, preset, automation, RDS, security, network, license or firmware value was written during this milestone. The previously documented contrast-only test remains the sole hardware write verification and restored the original value.
