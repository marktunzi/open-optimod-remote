# Phase 10: 6300 and 8700i Automation

> **Evidence status:** 29 October 2026. Original clients `6300PC.exe` 4.1.1.19 and `8700iPC.exe` 1.5.1.11 (unmodified, CrossOver, driven only through their own Win32 messages) against virtual units running original firmware: 6300 4.1.1.19 (192.168.1.173) and 8700i 1.5.1.11 (192.168.1.175). The app's checks ran in an isolated test build (port 15701). Both units were left without automation events.

## What the clients do

| | 6300 | 8700i |
|---|---|---|
| Functions after the presets in the Automation dialog's action list (`CB_GETLBTEXT` on control 2566) | `Stereo`, `Dual-Mono`, `Bypass`, `Exit Test` | the 5700i's 18 functions in the same order (`Bypass` … `Stereo Enc Delay Out`) |
| Saved file (New Event, Done; capture of the upload) | `Automation.orb63autom`, opcode 234, `OptimodVersion=<6300.50>` | `Automation.orb87autom`, opcode 235, `OptimodVersion=<8700.52>` |
| Upload header | FILETIME low/high, name, size, as the other models | same |

The event blocks are the same as the 5700i's (`auto_event_NN`, `AUTO SET …`, weekdays, `SET BY DAY/WEEK`, `AUTOMATION EVENT`). The firmware string tables were not a reliable source: the 5500i firmware's table mixes GPI functions, and the 8700i firmware has no `Dual-Mono` at all. Only the clients' own lists are used.

## App

`automation::available` now includes the 6300 and 8700i, with their own functions, version and extension. Tests: the captured new events render byte for byte (`renders_the_6300_and_8700i_clients_new_event`); the scripted 6300 and 8700i units take an upload under the client's file name and give it back (`preset_files_round_trip`).

On firmware (app API, test build):

| Step | 6300 .173 | 8700i .175 |
|---|---|---|
| Read: the event the client saved | 1 event, no function, daily 00:00 | 1 event, no function |
| Write `Exit Test` daily 06:30, read back | identical | identical |
| Remove all events, read back | none | none |
